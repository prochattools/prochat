Database migrations are where “it worked locally” dies.

In early SaaS, you can get away with:

- Dropping tables
- Resetting data
- Manual fixes

In production, those habits destroy trust.

This guide focuses on structural migration safety — not convenience.

---

# 1. Adopt a Forward-Only Mindset

In growing SaaS, migrations should be:

- Additive
- Backward-compatible
- Forward-moving

Avoid:

- Dropping columns immediately
- Renaming columns destructively
- Breaking schema assumptions instantly

Production-safe principle:

**Add first. Migrate data. Switch code. Remove later.**

---

# 2. Never Couple Schema Changes With Logic Changes Blindly

Bad pattern:

- Change column
- Deploy new code
- Assume old data works

Safer pattern:

1. Add new column
2. Deploy code supporting both old + new
3. Backfill data
4. Switch read logic
5. Remove legacy column later

Decouple structure and behavior.

---

# 3. Zero-Downtime Migration Basics

Zero-downtime means:

Users never experience broken queries during deploy.

Avoid:

- Blocking table locks on large tables
- Rebuilding indexes synchronously
- Large destructive updates during peak hours

Safer approach:

- Add nullable columns first
- Create indexes concurrently
- Backfill in small batches
- Monitor DB load during migration

Even small SaaS should think this way early.

---

# 4. Handling Large Tables Safely

If a table has:

- Thousands (or millions) of rows
- Active production usage

Avoid:

`UPDATE table SET new_column = value`

Instead:

- Process in chunks
- Use background jobs
- Limit write bursts
- Track progress state

Backfills should be controlled.

Not brute-forced.

---

# 5. Schema Versioning Discipline

Every migration should:

- Be committed
- Be deterministic
- Be reproducible

Avoid:

- Manual production edits
- Running SQL in dashboard directly
- “Temporary” fixes

Your database must be:

- Versioned
- Trackable
- Deployable

Migration history is part of your architecture.

---

# 6. Plan Rollback Before You Migrate

Before running migration, ask:

- Can I restore from backup?
- Is migration reversible?
- Does new code depend on new schema immediately?

Forward-only does not mean reckless.

Rollback plan must exist.

Even if rarely used.

---

# 7. Protect Multi-Tenant Systems During Migration

In multi-tenant SaaS:

- Schema mistakes affect all customers
- Cross-tenant bugs can surface during backfill

Revisit:
How to Design Multi-Tenancy Correctly in Your SaaS.

Before migration:

- Test with multiple tenants
- Validate tenant isolation still holds
- Ensure tenant_id constraints remain intact

---

# 8. Test Migration in Staging With Realistic Data

Local testing is not enough.

Staging should:

- Contain realistic data size
- Include multiple tenants
- Mirror production schema
- Simulate production queries

Migration safety depends on realism.

---

# 9. Migration Checklist Before Production

Before applying migration:

- Confirm backup exists
- Confirm migration script reviewed
- Confirm code supports both schema versions
- Confirm backfill plan defined
- Confirm monitoring active
- Confirm rollback path known

If any of these are unclear, pause.

---

# 10. Avoid AI-Generated Migration Shortcuts

AI may suggest:

- Dropping constraints
- Removing columns immediately
- Rewriting entire tables
- Combining structural changes into one migration

Never deploy migration code blindly.

Review every SQL statement.

---

# 11. Minimal Safe Migration Pattern for Early SaaS

For growing SaaS:

- One migration per logical change
- Additive first
- Backfill separately
- Remove legacy later
- Version-controlled
- Tested in staging

Simplicity + discipline = safety.
