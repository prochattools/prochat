Stripe integration is not a checkout button.

It is a lifecycle.

If billing is structured incorrectly, your SaaS will eventually:

- Grant access without payment
- Remove access incorrectly
- Break on upgrades
- Fail on renewals
- Lose revenue silently

This guide focuses on modeling billing correctly — not just connecting Stripe.

---

# 1. Understand the Subscription Lifecycle

A subscription is not a boolean.

It has states.

Stripe lifecycle includes:

- `incomplete`
- `trialing`
- `active`
- `past_due`
- `canceled`
- `unpaid`

Your database must reflect this lifecycle clearly.

Do not store:

`isPro: true`

Instead store:

- subscription_status
- current_period_end
- plan_id
- stripe_customer_id
- stripe_subscription_id

Structure first.

---

# 2. Webhooks Are the Source of Truth

Never rely solely on:

- Client-side redirects
- “Success” pages
- Immediate API responses

Stripe webhooks must:

- Validate signature
- Update subscription state
- Be idempotent
- Log failures

Every entitlement decision should be based on webhook-updated data.

If webhooks fail silently, revenue leaks.

---

# 3. Enforce Entitlements Server-Side

Feature gating must happen:

- In API routes
- Before sensitive operations
- Based on subscription state in your database

Never:

- Check Stripe directly from the frontend
- Trust client-passed plan values
- Hide UI and assume that equals enforcement

Billing is a backend concern.

---

# 4. Idempotency Is Not Optional

Webhooks can fire multiple times.

Your logic must:

- Detect duplicate events
- Prevent duplicate database updates
- Avoid double crediting or revoking

Use:

- Event IDs
- Processed-event logs
- Transaction boundaries

Without idempotency, billing becomes unstable.

---

# 5. Handle Failed Payments Explicitly

Many founders ignore `past_due` and `unpaid`.

You must define:

- Grace period?
- Immediate downgrade?
- Soft warning?
- Hard lock?

Your product must know what to do when payment fails.

Ignoring failed payments = delayed chaos.

---

# 6. Model Upgrades and Downgrades Carefully

When user upgrades:

- Do entitlements change immediately?
- Does it wait until next billing cycle?
- Does database reflect new plan instantly?

When user downgrades:

- Do features revoke immediately?
- At period end?

Define rules explicitly.

Ambiguity causes inconsistent user experiences.

---

# 7. Separate Billing From Feature Logic

Do not mix:

- Stripe logic
- Business logic
- Feature checks

Structure like:

Billing layer:
- Syncs Stripe → database

Entitlement layer:
- Reads database → enforces access

Feature layer:
- Executes only if entitlement layer approves

Clean separation reduces future refactors.

# 8. Avoid Client-Side Billing Decisions

Common AI mistake:

- Checking plan in frontend
- Enabling features based on local state
- Skipping server validation

Frontend can show:
“You need Pro to access this.”

Backend must enforce:
“Access denied.”

Always.

---

# 9. Test Billing Like an Attacker

Before production:

- Attempt to access Pro route without active subscription
- Cancel subscription and verify entitlement removal
- Simulate webhook failure
- Simulate duplicate webhook
- Simulate expired session with active billing

Billing should behave predictably.

If behavior is surprising, structure is weak.

---

# 10. Logging Is Critical

Log:

- Webhook receipt
- Signature validation result
- Subscription updates
- Entitlement changes

Without logs:

You cannot debug revenue issues.

---

# 11. Minimal Safe Billing Model for First SaaS

For early-stage SaaS:

You need:

- Stripe customer ID
- Stripe subscription ID
- subscription_status
- current_period_end
- plan_id
- Webhook handler with signature verification
- Server-side entitlement check

Nothing more.

Do not over-engineer.

But never under-structure.
