## Conversion thesis

The public platform is an **open-source adoption engine** and a trust-building product platform.

Its primary job is to move a qualified visitor from passive awareness into meaningful participation:

```text
Discover
→ Understand
→ Trust
→ Star
→ Install
→ Use
→ Learn
→ Give feedback
→ Contribute
→ Advocate
```

The website is successful when visitors do something verifiable with the product or community—not merely when they admire the design.

## Primary public outcomes

The public platform should increase:

- GitHub repository stars;
- repository visitors;
- verified installations or downloads;
- active testers;
- successful first-use completions;
- documentation completion;
- feedback submissions;
- GitHub issues;
- GitHub discussions or equivalent community participation;
- pull requests and other contributions;
- returning users;
- referrals and public advocacy;
- qualified managed-service inquiries from organizations.

## Business and product model

### Product path

ProChat Memory should be presented as a user-owned, local, portable product that people can inspect, install, use, test, and improve.

Subject to Mind and repository verification, the public product path is:

```text
free product
→ public repository
→ install locally
→ use with own memory
→ report feedback
→ contribute improvements
```

### Managed-service path

The product itself is not positioned as a traditional hosted SaaS purchase.

Organizations that want help may engage ProChat for a managed implementation, potentially including:

- assessment and planning;
- installation and deployment;
- workspace or repository setup;
- customization;
- integration with existing tools;
- migration and information structuring;
- training;
- governance and review workflows;
- maintenance and support.

The managed-service path must remain secondary on product-led pages. It should appear when a visitor has already understood the product and recognizes that organizational adoption requires assistance.

The website must not:

- imply that the open-source product is intentionally incomplete to force service purchase;
- hide self-installation or documentation paths;
- present managed services as a third software product;
- turn the homepage into a consultancy portfolio;
- claim service scope, pricing, response times, or guarantees that are not approved.

## Visitor lifecycle

### 1. Discover

Visitor question:

> What is ProChat Memory, and why should I care?

Required experience:

- clear promise;
- memorable visual model;
- no architecture dump;
- immediate evidence of local ownership and durable memory.

### 2. Understand

Visitor question:

> How is this different from notes, chat history, or another AI wrapper?

Required experience:

- capture, review, structure, retrieval, and reuse model;
- distinction between raw evidence and trusted memory;
- model-agnostic and portable architecture explained simply.

### 3. Trust

Visitor question:

> Why should I trust this with important memory?

Required experience:

- local files;
- Markdown-first storage;
- Git versioning;
- human review;
- inspectability;
- correction and supersession;
- honest product-stage language;
- founder credibility grounded in QA and verification.

### 4. Star

Visitor question:

> Is this worth following and supporting?

Required experience:

- prominent repository path;
- concise reason to star;
- visible activity and roadmap where verified;
- no forced signup before GitHub access.

### 5. Install

Visitor question:

> Can I get this running successfully?

Required experience:

- system requirements;
- quickstart;
- installation steps;
- expected outcome;
- troubleshooting;
- platform and version support.

### 6. Use

Visitor question:

> What should I do first to experience the product's value?

Required experience:

- one bounded first-use scenario;
- sample data or project where appropriate;
- clear trust/review workflow;
- explicit product limitations.

### 7. Learn

Visitor question:

> How do I use this well and safely?

Required experience:

- concepts;
- examples;
- memory lifecycle;
- correction and review;
- privacy and provider boundaries.

### 8. Give feedback

Visitor question:

> How can I report what happened without wasting time?

Required experience:

- structured feedback path;
- issue templates;
- reproduction guidance;
- privacy reminders;
- expected response or triage behavior only when approved.

### 9. Contribute

Visitor question:

> How can I improve the product?

Required experience:

- contribution guide;
- development setup;
- issue labels or starter tasks;
- testing requirements;
- code of conduct and governance where applicable.

### 10. Advocate

Visitor question:

> How can I help other people discover it?

Required experience:

- star/watch/follow prompts;
- shareable product explanation;
- examples and outcomes;
- truthful public milestones.

## Section rule

Every section must answer one explicit visitor question and move the visitor one step forward in the lifecycle.

A section should be removed or rewritten when it:

- repeats an earlier claim without new evidence;
- has no clear visitor question;
- has no relationship to adoption, trust, use, contribution, or qualified service inquiry;
- exists only because the reference template contains a similar block;
- introduces a CTA that competes with the page's primary purpose.

## Copywriting principles

### Clear

Use direct labels and concrete outcomes.

Prefer:

```text
Star ProChat Memory on GitHub
```

Over:

```text
Join the future
```

### Evidence-based

Claims must point to product behavior, repository evidence, documentation, tests, examples, or an explicitly labeled aspiration.

### Community-oriented

Invite participation without manufacturing social pressure.

Prefer:

```text
Use it in a real QA investigation and tell us what failed.
```

Over:

```text
Join thousands of innovators.
```

### Invitation over persuasion

The visitor should retain control. Do not use countdowns, false scarcity, forced signup, hidden repository links, or manipulative urgency.

### Confidence without hype

State the problem, model, current capability, and limitations precisely.

### GitHub-native

Use language familiar to open-source users:

- star;
- watch;
- clone;
- install;
- issue;
- discussion;
- pull request;
- contribute.

Do not use GitHub terminology when the action does not actually lead to GitHub.

### Managed-service clarity

Describe organizational help as deployment, customization, integration, training, governance, and support—not as a hidden license requirement.

## Conversion and design rules

- The design must make the primary action visually obvious.
- High visual quality must support comprehension and action, not delay them.
- Illustrations must explain memory behavior and reinforce adjacent copy.
- GitHub actions should use recognizable repository/star iconography where licensing permits.
- External-link behavior must be clear.
- Primary CTAs must be visible at important decision points without being repeated mechanically in every section.
- The page must not become a wall of GitHub buttons.
- Managed-service CTAs must use a different visual tier from product adoption CTAs.
- Mobile layouts must preserve the conversion hierarchy.
- Performance, accessibility, and trust are conversion requirements.

## Measurement framework

### Core events

Subject to privacy approval, the platform may measure:

- repository outbound click;
- star-intent click;
- installation-guide start;
- quickstart completion signal where technically and ethically appropriate;
- documentation search and dead ends;
- feedback-path click;
- issue/discussion/contribution click;
- managed-service inquiry start and completion.

### Metric quality rules

- Do not claim a GitHub star was created merely because a visitor clicked the button.
- Separate site click-through from confirmed GitHub outcomes.
- Do not fingerprint users.
- Do not collect product-memory content for marketing analytics.
- Do not optimize for engagement time when task completion is the real objective.
- Prefer aggregate, privacy-preserving metrics.
