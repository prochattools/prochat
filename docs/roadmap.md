## Roadmap principle

Build the memory foundation first, prove one repeated-work outcome, and expand only when the result is useful.

```text
memory foundation
→ one repeated task
→ review-ready output
→ human feedback
→ better future output
→ portable delivery
→ managed delivery
→ team and niche expansion
```

## Phase 1 — Strategy and naming alignment

Goal:

- keep mind and ProChat documentation synchronized
- maintain one product philosophy
- define the business/product naming hierarchy
- avoid coupling internal implementation identifiers to an undecided public name

Exit criteria:

```text
The business, flagship product, memory foundation, workflow packages, and niche derivatives have one clear naming architecture.
```

## Phase 2 — First time-saving demo

Goal:

Prove one repeated task can be prepared faster using reusable examples and context.

Recommended first demo:

```text
Founder or owner provides notes, old examples, and a client request.
The system prepares a reply draft, proposal outline, task instruction, and context summary.
```

Requirements:

- safe sample data
- visible before and after
- understandable in under five minutes
- human review step
- no complex infrastructure required for the demo

## Phase 3 — Work Memory v1

Goal:

Create a reusable memory structure for one person or team.

Minimum contents:

- good examples
- examples to avoid
- style and tone
- decisions and rules
- recurring formats
- project or client context
- reviewer feedback
- source references
- simple indexes

Exit criteria:

```text
The same memory improves more than one output without being re-entered manually.
```

## Phase 4 — Workflow Module v1

Goal:

Turn one repeated task into a reusable workflow.

Candidate first modules:

- founder delegation
- sales follow-up
- support reply
- proposal draft
- weekly status report
- content preparation

Exit criteria:

```text
The same type of input repeatedly produces a useful review-ready output.
```

## Phase 5 — Review and improvement loop

Goal:

Use human feedback to improve both memory and workflows.

Capture:

- approval or rejection
- edits
- missing context
- useful examples
- recurring corrections
- memory scope changes
- rules to promote, correct, or retire

Exit criteria:

```text
Later runs improve because reviewed work changed the system.
```

## Phase 6 — Portable demo and starter package

Goal:

Make the product easy to demonstrate, install, configure, deploy, and maintain.

Target package:

```text
config/
memory/
workflows/
inbox/
outputs/
review/
examples/
README.md
```

Delivery targets:

- ZIP or repository demo package
- safe sample memory and workflows
- short installation guide
- one-command or simple launcher where practical
- containerized option
- export and backup path
- reproducible technical setup

Exit criteria:

```text
A technical customer or ProChat operator can run the starter package in under thirty minutes.
```

## Phase 7 — Managed commercial launch

Goal:

Let customers use the product without operating the underlying infrastructure.

Possible entry points:

- email
- forms
- file drops
- shared folders
- manual upload
- API calls

Required:

- simple review experience
- logs and error visibility
- safe credential handling
- backup and export
- documented support process
- managed improvement offer

## Phase 8 — API and MCP interfaces

Goal:

Expose approved memory and workflows to other software and compatible AI clients.

API capabilities:

- submit input
- select memory scope
- run workflow
- retrieve output
- approve or reject
- submit feedback
- update or promote memory

MCP capabilities:

- search approved memory
- read scoped memory
- submit repeated work
- run approved workflows
- review output
- add feedback
- promote memory with permission

API and MCP remain implementation and integration surfaces, not the primary marketing message.

## Phase 9 — First managed customers

Goal:

Validate the commercial offer with one person or one team at a time.

Commercial sequence:

```text
first time-saving test
→ done-for-you launch
→ managed improvement
```

Measure:

- time saved
- output usefulness
- reviewer edits
- repeat usage
- support burden
- willingness to continue paying

## Phase 10 — Team and department rollout

Goal:

Expand useful personal or project memory into approved shared memory.

```text
personal memory
→ team-approved memory
→ department memory
→ company memory
```

Add:

- permissions
- memory scopes
- shared examples
- approval rules
- source traceability
- promotion and retirement controls

## Phase 11 — Niche derivatives

Goal:

Package the same foundation for specific roles or sectors.

```text
niche memory + niche workflows + review rules + delivery configuration
```

Possible derivatives:

- legal
- accounting
- agencies
- consulting
- real estate
- sales
- support
- content operations

A niche derivative should reuse the same core memory model, workflow contracts, review loop, and delivery interfaces.

## Phase 12 — Company and cross-project memory

Goal:

Preserve useful knowledge across teams and projects without losing scope or source history.

Required:

- source-traceable memory
- controlled promotion
- conflict handling
- freshness review
- exportability
- clear retirement rules
- evidence-aware retrieval

## Roadmap rules

- mind strategy leads implementation
- memory foundation before feature expansion
- one repeated task at a time
- examples before automation
- human review before trusted memory promotion
- portable formats where practical
- stable interfaces between memory and workflows
- simple demo before complex deployment
- managed delivery when self-installation adds unnecessary friction
- niche derivatives reuse one foundation
- public marketing sells outcomes, not architecture
